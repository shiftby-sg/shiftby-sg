# ShiftBy Website Implementation Workpacket

## Intent Summary

This workpacket materializes `SHIFTBY_WEBSITE_IMPLEMENTATION_INTENT_V1` into a governed execution structure for controlled website implementation. It exists to preserve implementation confidence through explicit authority, bounded phases, validation proof, and failure handling before any website execution begins.

## Authority Hierarchy

1. `SHIFTBY_WEBSITE_IMPLEMENTATION_INTENT_V1`
2. Core doctrine: `Execution changes. Understanding preserves confidence.`
3. Founder observation:
   - `Organizations preserve artifacts.`
   - `Organizations struggle to preserve understanding.`
4. Approved narrative sequence
5. Approved page designs under `plan/impl/design`
6. This workpacket control plane under `plan/impl`

## Scope

- Govern website implementation work from repository assessment through release readiness review
- Preserve authority, sequencing, validation, and evidence requirements
- Define execution phases `phase0` through `phase7`
- Define machine-readable status, validation, and failure models

## Exclusions

- No website implementation in this workpacket creation step
- No application source changes
- No package or runtime changes
- No deployment artifacts
- No generated website assets
- No content rewriting
- No approved design modification
- No doctrine reinterpretation

## Invariants

- Implementation must preserve doctrine and narrative authority
- Implementation must not reinterpret approved designs
- Approved designs under `plan/impl/design` are read-only authority
- Explorations remain investigations, not products
- AI remains a manifestation of the challenge, not the website thesis
- Validation evidence is required proof, not optional support material
- Release readiness requires human review
- Execution is phase-bounded and does not auto-progress

## Approved Narrative Sequence

1. Home
2. Capabilities
3. Where ShiftBy Helps
4. Perspective
5. Explorations
6. Services
7. About
8. Contact

## Design Authority Root

`plan/impl/design`

## Implementation Expectations

- Materialize the approved website only through bounded phases
- Preserve approved narrative sequence and page intent
- Preserve doctrine language and approved positioning
- Treat designs as implementation authority, not inspiration
- Keep generated artifacts derived from approved authority

## Validation Expectations

- Validate doctrine fidelity
- Validate narrative fidelity
- Validate design parity
- Validate responsiveness, accessibility, SEO, and discoverability
- Produce explicit evidence for each validation condition
- Do not self-approve release readiness

## Failure Classification Model

Failure handling is governed by `plan/impl/failure_classification.json`. Blocking failures include doctrine deviation, narrative deviation, design fidelity failure, SEO failure, LLM discoverability failure, accessibility failure, performance failure, mobile responsiveness failure, implementation boundary failure, deployment readiness failure, design authority not found, rejected wrong repo path, and control plane failure.

## Phases

- `phase0`: Repository Assessment
- `phase1`: Architecture Setup
- `phase2`: Design System Materialization
- `phase3`: Page Materialization
- `phase4`: SEO & LLM Layer
- `phase5`: Performance Optimization
- `phase6`: Validation
- `phase7`: Release Readiness Review

## Explicit Control Statements

- Implementation must not reinterpret approved designs.
- Explorations remain investigations, not products.
- AI remains a manifestation of the challenge, not the website thesis.
